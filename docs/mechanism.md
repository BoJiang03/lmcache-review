# 蒸馏机制：上线前 / 上线后

目标：把一个团队的 review 能力蒸馏进 AI 第一轮 review，并按领域逐步替代人工第一轮。每个仓库一套，各学各的（第一个用户是 LMCache 团队，下文的例子都来自 LMCache）。

原则：
- 单条发现的对错由团队行为判断，不依赖机制设计者的判断。
- reviewer 有什么就报什么，不限制条数。展示时 minor 和 nit 折叠，不删除。
- reviewer 和裁判的 effort 都是 high。

```
                   ┌──────────────────── 共用 ────────────────────┐
                   │ 规则库 rules/   信号库 signals/   领域表 areas │
                   └──────▲───────────────▲───────────────▲───────┘
                          │               │               │
   上线前（AI 不可见）     │               │               │    上线后（AI 可见）
   ─────────────────────  │               │               │  ─────────────────────
   回放 → 对比 → 归因 → 蒸馏 ─┘   被动信号 ──┘   晋级/回退 ──┘   展示 → 反应 → 蒸馏
            ▲                                                    │
            └────── 规则库的每个新版本都要先通过上线前的评估（回归门禁）──┘
```

## 共用部件

| 部件 | 内容 |
| --- | --- |
| 规则库 `rules/` | 两种条目：**原则**（principle，reviewer 应用的审查原则，从实例往上抽象，一个实例就够）和**知识**（knowledge，关于代码库或引擎的事实和不变量，按路径限定）。字段：when、expect、why、examples、paths、证据（人类评论 id）、n_prs（只作参考，不作门槛）。有版本号。reviewer 的 prompt 只加载与本 PR 改动路径相关的条目；条目有没有用由 test 上的翻转决定 |
| 信号库 `signals/` | 每条 AI 发现最后的结局（见下文），由脚本计算 |
| 领域表 `areas` | 领域（路径前缀）→ 所处阶段（上线前/上线后）、门槛、对照组比例 |
| Reviewer | 通用模型 + 规则库。每条发现带 `rule`（如果有）。schema v2 |
| 裁判 | 只做两件事：判断两条评论是不是同一个问题；给 human 独有的评论归因。不判断 AI 发现的对错 |

## 设计假设：小组件、可组合、可预测、回放

```
 prompt = 固定的 review 指令 + 规则库（一条条小条目）
                                   │
 改一条规则 ──► 只回放这条规则的来源评论（和它替换/影响的条目的已证明 case）
                                   │
                         命中 → 保留；丢了已证明的 case → 撤回
```

prompt 被拆成很多小组件（规则条目），像软件拆成模块：规则是模块，它的来源评论是单元测试，vet 是只跑受影响测试的 CI。整套机制的成本靠三个假设：

1. **可组合**：一条规则的效果主要取决于它自己的写法，和其他规则关系不大。
2. **可预测**：规则在它的来源评论上会触发，就说明在同类情况下也会触发。
3. **局部回放够用**：改一条规则，只回放和它相关的样本，就能判断这次改动对不对，不必每次全量重跑。

支撑这三个假设的结构：
- **rule check 单独成一个 agent**，对每条适用的规则逐条给出判定。规则塞在一个大 prompt 里时会互相挤掉，可组合性不成立；逐条强制判定之后才基本成立。
- **规则只在 rule check 里生效**：v0007 上，靠规则找到的命中全都有 rule check 参与。所以 vet 只回放 rule check（`-ro`）就够了，不用重跑主 review。
- **每次改动都留下"规则 ↔ 来源评论"的链接**，回放时知道该跑哪些样本。

  | 改动 | vet 回放什么 |
  | --- | --- |
  | add | 它的来源样本：漏掉的点现在找到了吗（没有自己证据的新条目直接丢弃） |
  | revise / RETRY 改写 | 它的来源和触发改动的 case：仍然找到，且 case 修好了吗 |
  | generalize / merge | 新条目带着被替换条目证据的并集；回放被替换条目的每个来源 |
  | absorb B 进 A | B 的证据移到 A，A 要对 B 的样本负责；回放 B 的所有来源 |
  | side effect | 和改动条目相连的条目：抽它们的部分来源 |

已知的弱点（目前都没有测）：
- 规则之间的干扰：新加一条宽泛的规则，可能让别的规则判得更松或更严，而这些没改的规则不会被回放到。
- 规模：规则库越大，干扰越明显。分阶段加载（先按 when 挑，再逐条判）只能缓解。
- 模型升级：同一个 prompt 换了模型，所有"已证明"的结论都要重新确认。每个 run 记下实际用的模型（`model`），模型变了缓存不再命中；没记录的旧 run 算"未知"，照常命中，报告里标出。
- 测量本身：缓存冷热会让成本对比失真；单次运行的噪声靠"失败的 case 再跑一次"来压。vet 按多次运行的计数下结论（报告里写 `NEW 2/2`、`NEW 3/4`）：effect 2/2 有效，1/2 补 2 次、≥3/4 有效；side effect 只有 NEW 0/2（或 1/3）且 BASE 两次里至少中一次才算 LOST，NEW 1/2 补一次、≥2/3 算保留。round 在 distill 前把有新 miss 的样本用同一个 reviewer 再跑一次（`#r2`，预算 `[budget.round] confirm`）：第二次找到的 miss 在 ledger 里记 `hits: "1/2"`、`flaky`，照样送 distill，排在两次都漏的后面；没跑成的记 `unconfirmed`；输出一行 `confirm: N misses, K flaky, $X`。重复运行存为 `<reviewer>#r<k>`。

以后要验证时，可以定期做一次全量回放（`vet --all`），统计没改的规则因为别的规则改动而丢掉已证明 case 的比例。比例低，说明局部回放可靠；比例高，就要把回放范围扩到会互相影响的规则。

## 泛化的分工：distill 和 compress

改规则库的有两处，按各自看得到的信息分工（2026-11-24 定，下一批起测）：

| | distill（每轮） | compress |
| --- | --- | --- |
| 看得到 | 新评论原文、thread、diff + 整本规则库 | 只有规则库（条目文字、例子、证据 id） |
| 负责 | **评论 ↔ 条目**：把新评论放到对的位置 | **条目 ↔ 条目**：已有条目之间合并、提升、压短 |
| 上限 | reviewer 说出的原则 | 被合并条目的证据合起来撑得住的程度 |

- **write**：优先并入（evidence）或泛化（generalize）已有条目；新建（add）要写出最接近的已有条目（`closest`）和为什么不能并入（`why_new`），写不出就泛化。不合并已有条目。
- **consolidate**（distill 内，每轮）：增量 compress，每个合并或吸收都至少包含一条本轮新条目；已有条目之间的合并留给 compress。
- **compress**（全书）：定期整理，处理增量版看不到的远距离合并和过长条目。目前仍在规则库超过 10k 词时触发。
- **长度**：when + expect 合计约 80 词以内，子情况、机制和实例放进 examples（最多 2 条）；只有 RETRY 证明短的写法不触发时才写长。
- 两边都过 vet，合并的证据是来源证据的并集。

衡量：distill 看本轮新条目里只有 1 条证据的比例（应该低）；compress 和整体看"每条评论摊多少词"（应该逐轮下降）。v0014–v0020 这个数一直在 85–94 词，45 条里 22 条只有 1 条证据。

## 让 workflow 自己做对（2026-11-24，从 8 条 needs_human 复盘）

needs_human 不该靠人逐条改，而是暴露 workflow 的缺陷。复盘后的修复：

| 现象 | 缺陷 | 修复 |
| --- | --- | --- |
| 作者同意但推迟（加 TODO）被判 contested | attribute 把"没改"等同于"反对" | 同意但推迟 = learnable；用可核查事实（formatter、规范、CI）证明要求错 = rejected；规划类问题先判 context |
| 重试时把评论再挂到同一条规则上，原样失败 | write 不知道规则为什么没触发 | vet 把 rule check 对该规则的判定（applies / violated / why）写进 tries，write 重试时按这个原因改 |
| 早期失败的评论永远停在 needs_human | needs_human 是终点 | `requeue_parked`：distill 提示词变了，或规则库出现新的/改过的相关条目（COVERAGE 判断），就放回 to_distill；每条最多 2 次；人写的决定不重开 |
| 文档说法要和调用点核对，rule check 只能判"适用" | 不带工具的 rule check 看不到 diff 以外的代码 | rule check 输入加 SYMBOLS：diff 定义的名字和文档里提到的名字，在整个仓库里的定义和使用位置（grep，确定性预处理） |
| "报 bug 时要求补回归测试"写成规则永远不触发 | 规则只作用于 diff，看不到 reviewer 自己的 finding | 这类关于 finding 写法的要求放进 reviewer.md；以后攒多了再考虑"作用于 finding 的规则" |

## 只把真正测过的当成试过（2026-11-25，batch 7/8）

| 现象 | 缺陷 | 修复 |
| --- | --- | --- |
| vet 碰到成本上限仍提升了规则库 | 有失败的条目时 verdict 先判 FAIL，盖过 INCOMPLETE | 只要有没跑的 case 就是 INCOMPLETE，保留候选 |
| 没测到的条目也算一次失败 | tries 不分"测了没用"和"没测" | "kept but not tested" 不计入 MAX_TRIES |
| 为某条评论改写的旧条目从不在该评论上测 | vet 只测新挂上的 evidence | vet 测所有挂着本轮目标评论的条目（`targets`） |
| needs_human 回不来 | requeue 把"出现在 try 里"当成"测过"，且靠 COVERAGE 猜覆盖 | 只认 vet 真正跑过且文字没改过的条目；挂着该评论的条目直接算覆盖 |
| vet 部分保留被叫做 FAIL | 命名 | ALL KEPT / PARTLY KEPT / NONE KEPT / INCOMPLETE |

## compress 的两个问题（2026-11-25，batch 8）

68 条、10158 词的书，3 份草稿各只提 1–2 个 merge，多数票后剩 1 个，vet 又撤了它：几乎没压。

| 问题 | 原因 | 修复 |
| --- | --- | --- |
| 压得太少 | 草稿只挑最有把握的；多数票再筛 | 先把整本书分组再逐组 merge；不投票，取所有草稿的 merge（重叠取多数草稿提的），vet 是唯一的门 |
| 压完丢 case | 为了压到一半词数，删掉了让条目触发的区分条件（"包了一层也算重复"） | 上限 50%→70%；merge 必须保留决定触发的条件和知识条目的事实；撤销时记下 rule check 的理由（不适用 → 改 when；适用但未违反 → expect 丢了条件），同一 round 再压一次（`[compress] tries = 2`） |

## 上线前（AI review 不展示）

人的 review 是独立的，就是标准答案。**目标：减少可学的 human 独有。**

```
 train 样本 ──▶ reviewer vN ──▶ 与人对比 ──▶ human 独有 ──▶ 归因 ──┬─ 可学 ──▶ 候选规则 ──▶ 规则库 vN+1
                                    │                              ├─ 缺上下文 ──▶ 记录（补上下文的需求）
                                    │                              └─ 不算问题（问句/表扬/标错）──▶ 排除
                                    └─▶ AI 独有 ──▶ 被动信号（只监控）

 test 样本 ──▶ vN 与 vN+1 对比（逐条翻转）──▶ 净修复 > 0 才接受
 新 PR（隐藏运行）──▶ 领域门槛 ──▶ 上线
```

1. **回放**：reviewer 在 train 样本上运行，每个样本是 (PR, 人 review 过的 commit)。工作区只包含 t0 时刻之前可见的内容。
2. **对比**：裁判把每条人类 change request 和 AI 发现做匹配，得到三类：都有 / human 独有 / AI 独有。
3. **归因**：每条 human 独有的评论归入一类：
   - 可学：团队规则、偏好、约定、需要同步的地方；
   - 缺上下文：线下讨论过的决定、运行时行为、仓库外的代码；
   - 不算问题。
4. **蒸馏**：可学的漏报先聚类，再写成候选规则，附上证据，和已有规则去重后得到规则库 vN+1。
5. **验收**：在 test 上比较 vN 和 vN+1，看每条人类评论从漏到中或从中到漏的翻转，而不是看汇总数字，因为单次运行的波动有 ±15 个点。净修复 > 0 才接受新版本。holdout 只在上线门槛处使用一次。
6. **监控（不作为约束）**：AI 独有的数量、被动信号印证率、严重程度是否被标低（人的 change request 被 AI 标成 minor/nit 的比例）。
7. **新 PR 隐藏运行**：对人 review 过的新 commit，用 t0 之前的工作区跑一次，不展示。这是最接近真实上线的检验，数据也不可能出现在训练集里。按批运行，量由预算决定。

**上线门槛（按领域，数值由维护者定）**：新 PR 隐藏运行连续 N 个，可学的 human 独有率 ≤ X，并通过 holdout。

被动信号（脚本计算，免费），也用来校准裁判：

| 结局 | 判定方法 |
| --- | --- |
| 人当场提了 | 裁判匹配 |
| 人后来也提了 | 同一 PR 后续 commit 上的人类评论与该发现匹配 |
| 代码被改了 | 后续 commit 改动了该发现的 primary location（弱信号） |
| 合并后被修了 | 合并后的 fix/revert commit 改动了该位置 |

## 上线后（AI review 对人可见）

人的评论不再独立，主要信号变成对 AI 评论的反应。

**目标：减少上线 PR 上人看过 AI review 后还要补充的问题。** 严重问题的补充率趋近 0，就可以撤掉该领域的人工第一轮。
补充少了可能是 AI 覆盖到了，也可能是人变懒了，所以设两条护栏：
- **对照组 human 独有率不上升**：对照组的人是独立的，用来排除“人变懒”造成的假下降；
- **合并后缺陷率不上升**：合并后 fix/revert 碰到本 PR 代码的比例，这是最终的质量结果。

监控：否定率（维护者的时间成本）。不限制发现条数；被否定的内容进抑制规则，否定率过高会触发回退。

```
 新 PR ──▶ 分组 ──┬─ 上线 PR ──▶ AI review 可见（blocker/major 展开，minor/nit 折叠，折叠也算可见）
                 │                ├─▶ 对每条发现的反应 ──▶ 采纳 → 规则加权 / 否定 → 抑制规则
                 │                └─▶ 人在 AI 之后补充的评论 ──▶ human 独有 ──▶ 同上线前的归因和蒸馏
                 └─ 对照组 k% ──▶ AI 照常运行但不展示 ──▶ 用上线前的方法测 human 独有率（无偏）

 规则库新版本 ──▶ 先通过上线前 test 评估（回归门禁）──▶ 部署
```

1. **触发**：上线后必须决定什么时候运行（待定，见下文）。
2. **分组**：按 PR 随机分。对照组的 AI 照常运行但不展示，作用有两个：
   - 持续给出无偏的 human 独有率；
   - 和上线 PR 比较人类评论的数量与深度，检测人是否因为有 AI 而变懒。
3. **展示**：主要位置在 diff 里的发现作为 inline 评论，其余的放在 review 正文。minor 和 nit 折叠。
   折叠的发现也算已展示：对它们的反应计入采纳/否定；人补充的评论只要匹配上任何一条 AI 发现（包括折叠的），就不算补充。
4. **反应信号**：

   | 结局 | 判定方法 |
   | --- | --- |
   | 采纳 | 下一个 commit 改动了该位置，或者有 👍，或者作者回复认可 |
   | 否定 | 有 👎，或者回复不同意，或者没改代码就 resolve |
   | 无反应 | 单独统计，不算错 |
5. **蒸馏**（与上线前是同一个 `distill`，只是输入不同）：
   - 人在 AI 之后补充的、AI 没覆盖到的评论，走和上线前一样的归因和蒸馏流程。
   - 被否定的发现，聚类成“不要提 X”的抑制规则（规则库加 `kind: avoid` 区分；上线后再实现）。
   - 人附和 AI 的评论不算新证据，这是为了防止自我强化。
6. **回退**：任一条件满足就自动退回上线前模式：
   - 对照组 human 独有率超过门槛；
   - 合并后缺陷率上升；
   - 否定率超过门槛。
7. **撤掉人工第一轮（按领域）**：上线 PR 上严重问题的人补充率连续 N 个 PR ≤ X，且两条护栏都在线。之后人只做第二轮 review。

## 需要人来定的（都是策略问题，不需要 review 能力）

- 领域怎么划分、每个领域的门槛 N / X、对照组比例 k
- 上线后的触发时机（例如 ready for review 时，或者手动请求 `/review`）
- 展示渠道（GitHub 评论 / 先只给维护者看）。这是对外动作
- 隐藏运行的预算

## 工具（上线前）

命令和参数见 `docs/usage.md`，这里只列它们在机制里的位置。reviewer 的命名规则是
`<prompt>[+<规则库>][@<effort>][-rc|-ro]`，例如 `pdba46ca9+v0032@medium-rc`：`-rc` 是生产 reviewer（主 review + rule check），`-ro` 只跑 rule check（vet、retain 用它回放）。付费命令有 `--max-cost`，达到上限后就不再发起新的调用。所有命令都不会往 GitHub 发任何东西。

| 命令 | 在机制里的位置 |
| --- | --- |
| `lmreview sync` | 增量拉取最近更新过的 PR，重建样本（免费） |
| `lmreview round PR[:commit] ...` | 一轮：回放 → 判分 → 确认新 miss → distill + vet 直到评论落定；规则库超过 `[compress]` 词数时 compress + vet |
| `lmreview judge` | 对比：把人类评论拆成点，和 AI 发现匹配，记进 ledger（covered / to_distill） |
| `lmreview distill` | 归因 → 写 → consolidate，得到候选规则库 |
| `lmreview vet` | 局部回放（`--all` 全量），通过的部分成为下一个版本，失败的评论带着原因回到 to_distill |
| `lmreview retain` | 用 rule check 重跑已学会的点，不是每次都命中的送回 to_distill |
| `lmreview compress` | 全书整理（trim / merge），结果是候选，再过 vet |
| `lmreview review PR` | review 一个 PR 的当前版本（只在本地输出） |
| `lmreview status` / `init` / `rollback` / `discard` | 查看 / 初始化 / 移动状态 |

```bash
lmreview sync
lmreview round 3359 3461:a58f5c9c    # 在这些样本上学一轮
lmreview status
git add lmreview/state && git commit  # 发布新版本
```
