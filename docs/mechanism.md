# 蒸馏机制：上线前 / 上线后

目标：把 LMCache 团队的 review 能力蒸馏进 AI 第一轮 review，并按领域逐步替代人工第一轮。

原则：
- 单条发现的对错由团队行为判断，不依赖机制设计者的判断。
- reviewer 有什么就报什么，不限制条数。展示时 minor 和 nit 折叠，不删除。
- reviewer 和裁判的 effort 都是 high。

```
                   ┌──────────────────── 共用 ────────────────────┐
                   │ 规则库 rules/   信号库 signals/   领域表 areas │
                   └──────▲───────────────▲───────────────▲───────┘
                          │               │               │
   上线前（AI 不可见）     │               │               │    上线后（AI 可见）
   ─────────────────────  │               │               │  ─────────────────────
   回放 → 对比 → 归因 → 蒸馏 ─┘   被动信号 ──┘   晋级/回退 ──┘   展示 → 反应 → 蒸馏
            ▲                                                    │
            └────── 规则库的每个新版本都要先通过上线前的评估（回归门禁）──┘
```

## 共用部件

| 部件 | 内容 |
| --- | --- |
| 规则库 `rules/` | 每条规则包含：id、描述、适用路径/组件、证据（人类评论链接）、统计（命中次数、被采纳次数、被否定次数）。有版本号。reviewer 的 prompt 只加载与本 PR 改动路径相关的规则 |
| 信号库 `signals/` | 每条 AI 发现最后的结局（见下文），由脚本计算 |
| 领域表 `areas` | 领域（路径前缀）→ 所处阶段（上线前/上线后）、门槛、对照组比例 |
| Reviewer | 通用模型 + 规则库。每条发现带 `rule`（如果有）。schema v2 |
| 裁判 | 只做两件事：判断两条评论是不是同一个问题；给 human 独有的评论归因。不判断 AI 发现的对错 |

## 上线前（AI review 不展示）

人的 review 是独立的，就是标准答案。**目标：减少可学的 human 独有。**

```
 train 样本 ──▶ reviewer vN ──▶ 与人对比 ──▶ human 独有 ──▶ 归因 ──┬─ 可学 ──▶ 候选规则 ──▶ 规则库 vN+1
                                    │                              ├─ 缺上下文 ──▶ 记录（补上下文的需求）
                                    │                              └─ 不算问题（问句/表扬/标错）──▶ 排除
                                    └─▶ AI 独有 ──▶ 被动信号（只监控）

 test 样本 ──▶ vN 与 vN+1 对比（逐条翻转）──▶ 净修复 > 0 才接受
 新 PR（隐藏运行）──▶ 领域门槛 ──▶ 上线
```

1. **回放**：reviewer 在 train 样本上运行，每个样本是 (PR, 人 review 过的 commit)。工作区只包含 t0 时刻之前可见的内容。
2. **对比**：裁判把每条人类 change request 和 AI 发现做匹配，得到三类：都有 / human 独有 / AI 独有。
3. **归因**：每条 human 独有的评论归入一类：
   - 可学：团队规则、偏好、约定、需要同步的地方；
   - 缺上下文：线下讨论过的决定、运行时行为、仓库外的代码；
   - 不算问题。
4. **蒸馏**：可学的漏报先聚类，再写成候选规则，附上证据，和已有规则去重后得到规则库 vN+1。
5. **验收**：在 test 上比较 vN 和 vN+1，看每条人类评论从漏到中或从中到漏的翻转，而不是看汇总数字，因为单次运行的波动有 ±15 个点。净修复 > 0 才接受新版本。holdout 只在上线门槛处使用一次。
6. **监控（不作为约束）**：AI 独有的数量、被动信号印证率、严重程度是否被标低（人的 change request 被 AI 标成 minor/nit 的比例）。
7. **新 PR 隐藏运行**：对人 review 过的新 commit，用 t0 之前的工作区跑一次，不展示。这是最接近真实上线的检验，数据也不可能出现在训练集里。按批运行，量由预算决定。

**上线门槛（按领域，数值由维护者定）**：新 PR 隐藏运行连续 N 个，可学的 human 独有率 ≤ X，并通过 holdout。

被动信号（脚本计算，免费），也用来校准裁判：

| 结局 | 判定方法 |
| --- | --- |
| 人当场提了 | 裁判匹配 |
| 人后来也提了 | 同一 PR 后续 commit 上的人类评论与该发现匹配 |
| 代码被改了 | 后续 commit 改动了该发现的 primary location（弱信号） |
| 合并后被修了 | 合并后的 fix/revert commit 改动了该位置 |

## 上线后（AI review 展示）

人的评论不再独立，主要信号变成对 AI 评论的反应。**目标：保持低 human 独有率，同时把噪音压下去。**

```
 新 PR ──▶ 分组 ──┬─ 展示组 ──▶ AI review 展示（blocker/major 展开，minor/nit 折叠）
                 │                ├─▶ 对每条发现的反应 ──▶ 采纳 → 规则加权 / 否定 → 抑制规则
                 │                └─▶ 人在 AI 之后补充的评论 ──▶ human 独有 ──▶ 同上线前的归因和蒸馏
                 └─ 对照组 k% ──▶ AI 照常运行但不展示 ──▶ 用上线前的方法测 human 独有率（无偏）

 规则库新版本 ──▶ 先通过上线前 test 评估（回归门禁）──▶ 部署
```

1. **触发**：上线后必须决定什么时候运行（待定，见下文）。
2. **分组**：按 PR 随机分。对照组的 AI 照常运行但不展示，作用有两个：
   - 持续给出无偏的 human 独有率；
   - 和展示组比较人类评论的数量与深度，检测人是否因为有 AI 而变懒。
3. **展示**：主要位置在 diff 里的发现作为 inline 评论，其余的放在 review 正文。minor 和 nit 折叠。
4. **反应信号**：

   | 结局 | 判定方法 |
   | --- | --- |
   | 采纳 | 下一个 commit 改动了该位置，或者有 👍，或者作者回复认可 |
   | 否定 | 有 👎，或者回复不同意，或者没改代码就 resolve |
   | 无反应 | 单独统计，不算错 |
5. **蒸馏**：
   - 人在 AI 之后补充的、AI 没覆盖到的评论，走和上线前一样的归因和蒸馏流程。
   - 被否定的发现，聚类成“不要提 X”的抑制规则。
   - 人附和 AI 的评论不算新证据，这是为了防止自我强化。
6. **回退**：任一条件满足就自动退回上线前模式：
   - 对照组 human 独有率超过门槛；
   - 否定率超过门槛；
   - 展示组的人类评论量相对对照组明显下降，并且漏报上升。

## 需要人来定的（都是策略问题，不需要 review 能力）

- 领域怎么划分、每个领域的门槛 N / X、对照组比例 k
- 上线后的触发时机（例如 ready for review 时，或者手动请求 `/review`）
- 展示渠道（GitHub 评论 / 先只给维护者看）。这是对外动作
- 隐藏运行的预算
