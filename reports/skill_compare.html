lmreview 漏掉的是什么

漏掉 18 个要点，另有 11 条提问（提问不是 AI 该回答的）。

  • blocker 1：rebase 到 dev 之后接口签名不匹配，导致 mypy 报错。这需要知道当时的 base 分支状态，离线回放拿不到。
  • major 3：reserve_write 和 reserve_read 之间 key 可能被驱逐的竞态；lookup 状态代码要更模块化；异步 L2 读锁导致的 flaky 测试。
  • minor 7：大多是需要项目背景的取舍，比如拆成单独的 PR、把函数挪到单独文件、两个监控指标重叠、删掉的 docstring 里有一句该保留、单测里不要 import vllm。
  • nit 7：口味型意见，比如改名（num_groups → num_object_groups）、辅助函数放到类末尾、import 放顶部、撤回不必要的改名。

这些漏掉的评论会进入学习流程，变成规则。学过的组命中更高，就是这么来的。

skill 只有 error / warning / info 三级，没有 blocker 这一级，所以只列 error 一行，按 major 来比。"判分模型认为成立"是 AI 自己的判断，不是 gold，还需要人逐条确认。

lmreview 报的深层问题更多，有四个原因：

  • 侧重正确性：prompt 要求报所有真实问题，正确性排第一，发现 bug 还要给出回归测试。blocker/major 中带"崩溃、泄漏、竞态、数据错乱"这类字眼的，lmreview 有 45 条，skill 有 28 条。
  • 跟进之前的 review：之前评论过、这一版还没修好的问题会再报一次。lmreview 有 9 条属于这一类，skill 0 条。
  • 可以查 vLLM 源码：用来核对 PR 对 vLLM 行为的假设。提到 vLLM 的条目，lmreview 22 条，skill 11 条。
  • 级别划分：blocker/major 只留给行为错误。规范类问题两边都是 12 条。

配置和附带结论

  • lmreview：p29d23a9f+v0032@medium-rc。主审 medium，带 skill 的检查清单、设计文档检查、批量读取，只输出 JSON。rule check 用 low，和主审并行，不带工具。之后用一次小的 Sonnet 调用去掉 rule check 里与主审重复的条目。
  • skill：今天的 .claude/skills/pr-review/SKILL.md 加 docs/coding_standards.md，离线运行，然后用一次调用把 Markdown 报告抽成 JSON。
  • high 换成 medium（6 个样本）：lmreview 命中 70% → 70%，成本降 25%；skill 命中 59% → 49%。
  • 去重：20 个 run 中，rule check 的 72 条 findings 去掉了 25 条，人类评论命中损失 0，每个 PR 约 $0.011。

局限：每组只有 10 个样本；没学过的组都是较新的 PR（#5000 以后），学过的组是 #3200–#4700，所以两组之间的差异还混有时间因素；#3869 一个样本就占学过组 17 个要点；判分是 AI 盲评。数据在 data/skill_compare/，脚本是 scripts/skill_compare.py。
