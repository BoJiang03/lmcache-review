Missed by all three

lmreview missed 17 points, and /pr-review and /code-review missed all 17 as well. No point was caught by another reviewer and missed by lmreview.

  • 1 blocker: after rebasing on dev, interface signatures no longer match and mypy fails (#5478). This needs the base branch's state at the time, which offline replay does not have.
  • 2 major: a race where a key can be evicted between reserve_write and reserve_read (#3869); a flaky test caused by an async L2 read lock (#5478).
  • 8 minor: mostly trade-offs that need project context, such as splitting into a separate PR, moving a function to its own file, two overlapping metrics, two sentences in a removed docstring that should stay, and not importing vllm in unit tests.
  • 6 nit: matters of taste, such as renames (num_groups → num_object_groups, rust_io), using itertools.groupby, moving an import to the top, and reverting an unneeded rename.

#3869 alone accounts for 7. Missed comments feed the learning loop and become rules; that is where the higher recall on learned PRs comes from.

lmreview reports the most deep issues, for four reasons:

  • Correctness first: the prompt asks for every real problem, correctness first, and a regression test for each bug found.
  • Follows up earlier reviews: an issue raised before and still not fixed in this revision is reported again.
  • Can read vLLM source: to check the PR's assumptions about vLLM behavior.
  • Severity levels: blocker/major is reserved for wrong behavior. On standards issues the three are about even.

/code-review also hunts for bugs and reports plenty, but about 30% are judged invalid; without the PR description and project standards it has more false alarms.

Configuration and side findings

  • lmreview: p990f2d2e+v0032@medium-rc. Main review on Opus medium, with the /pr-review checklist, a design-doc check and batched reads, JSON output only. Rule check on medium, in parallel with the main review, without tools. Then one small Sonnet call removes rule-check findings that repeat a main-review finding.
  • /pr-review: .claude/skills/pr-review/SKILL.md plus docs/coding_standards.md from LMCache dev d0959e0, run offline.
  • /code-review: /code-review medium. Severity mapping: important → major, pre_existing → minor, nit → nit.
  • High to medium (6 samples, measured before this config): lmreview recall 70% → 70% with 25% lower cost; /pr-review recall 59% → 49%.
  • Dedupe: about $0.015 per PR. Checked one by one when the rule check ran on low: 25 of 72 findings removed, no human-point hit lost.

Limits: only 10 samples per group; the unlearned PRs are all newer (#5000 and up) and the learned ones are #3200–#4700, so the gap between groups is mixed with time; #3869 alone has 17 of the learned group's points; grading is a blind AI judge. lmreview 对比 /pr-review 和 /code-review

20 个历史 PR 样本：学过的 10 个，没学过的 10 个。三方都用 Opus 5.5 medium，离线回放，同一个盲评判分器。2026-11-26。

比的是哪三个 review

名称来源用的版本
lmreview我们自己的 reviewer（仓库 BoJiang03/lmcache-review）。主审之外还有 rule check，规则由 rulebook 提供；rulebook 是从 LMCache 维护者的历史评论里学出来的。正式配置 p990f2d2e+v0032@medium-rc：主审 Opus medium；rule check medium，逐条对照 rulebook v0032 的 49 条规则，和主审并行运行。
/pr-reviewLMCache 仓库自带的 Claude Code skill：.claude/skills/pr-review/SKILL.md，它会读 docs/coding_standards.md。由 LMCache 维护者编写。LMCache dev 分支 d0959e0（2026-11-09）里的版本：SKILL.md 最后修改于 bed12fc（2026-11-08），coding_standards.md 最后修改于 5b9db86（2026-11-06）。每个样本用的都是这一版，没有用 PR 当时的版本。
/code-reviewClaude Code 内置的 skill，任何仓库里都能直接用 /code-review 调用，不针对 LMCache。Claude Code 2.1.332 自带的版本，参数为 /code-review medium。按开发者在本地 review 改动的方式运行：PR 的改动作为未提交的改动，没有 PR 描述、历史评论和编码规范。

三方都漏掉的

lmreview 漏了 17 个要点，这 17 个 /pr-review 和 /code-review 也都漏了。没有哪个要点是别人抓到而 lmreview 没抓到的。

  • blocker 1：rebase 到 dev 之后接口签名不匹配，mypy 报错（#5478）。这需要知道当时 base 分支的状态，离线回放拿不到。
  • major 2：reserve_write 和 reserve_read 之间 key 可能被驱逐的竞态（#3869）；异步 L2 读锁导致的 flaky 测试（#5478）。
  • minor 8：大多是需要项目背景的取舍。比如拆成单独的 PR，把函数挪到单独文件，两个监控指标重叠，删掉的 docstring 里有两句该保留，单测里不要 import vllm。
  • nit 6：口味型意见，比如改名（num_groups → num_object_groups、rust_io）、用 itertools.groupby、import 放顶部、撤回不必要的改名。

#3869 一个 PR 占了 7 个。这些漏掉的评论会进入学习流程，变成规则；学过的组命中更高，就是这么来的。

lmreview 报的深层问题最多，原因有四个：

  • 侧重正确性：prompt 要求报出所有真实问题，正确性排第一；发现 bug 时还要给出回归测试。
  • 跟进之前的 review：之前评论过、这一版还没修好的问题，会再报一次。
  • 可以查 vLLM 源码：用来核对 PR 对 vLLM 行为的假设。
  • 级别划分：blocker/major 只给行为错误。规范类问题三方差不多。

/code-review 也专找 bug，报得不少，但三成被判不成立；它没有 PR 描述和项目规范，误报更多。

配置和附带结论

  • lmreview：p990f2d2e+v0032@medium-rc。主审 Opus medium，带 /pr-review 的检查清单、设计文档检查、批量读取，只输出 JSON。rule check medium，和主审并行运行，不带工具。之后用一次 Sonnet 小调用，去掉 rule check 里和主审重复的条目。
  • /pr-review：LMCache dev d0959e0 里的 .claude/skills/pr-review/SKILL.md 加 docs/coding_standards.md，离线运行。
  • /code-review：/code-review medium。级别映射：important → major，pre_existing → minor，nit → nit。
  • high 换成 medium（6 个样本，换配置前测的）：lmreview 命中 70% → 70%，成本降 25%；/pr-review 命中 59% → 49%。
  • 去重：每个 PR 约 $0.015。rule check 为 low 时逐条检查过：72 条去掉 25 条，没有误删人类评论的命中。

局限：每组只有 10 个样本；没学过的组都是较新的 PR（#5000 以后），学过的组是 #3200–#4700，所以两组之间的差异还混有时间因素；#3869 一个样本就占学过组 17 个要点；判分是 AI 盲评。数据在 data/skill_compare/，脚本是 scripts/skill_compare.py。
